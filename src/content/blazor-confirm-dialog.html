Awaitable Confirm Dialog

Ask the user "are you sure?" with a single await in the middle of a method — no state flag, no second handler for the "yes" branch. A small scoped service holds a TaskCompletionSource, and one host component rendered once in the layout shows the modal.

Why a service instead of a component per page

The usual Blazor approach is a showConfirm bool, a modal in the markup, and a separate OnConfirmed() method that carries on with whatever the button started. That splits one decision across two methods and repeats the modal markup on every page. Here the call site reads top to bottom, exactly like confirm() in JavaScript, and the modal exists in one place.

The service

It never touches the UI. It stores the current request, raises Changed, and hands back a Task<bool> that completes when something calls Answer.

Services/ConfirmService.cs 
public record ConfirmRequest(
    string Title,
    string Message,
    string ConfirmText,
    bool Danger,
    IReadOnlyList<string> Details);

public class ConfirmService
{
    private TaskCompletionSource<bool>? pending;

    public event Action? Changed;

    public ConfirmRequest? Current { get; private set; }

    public Task<bool> AskAsync(
        string title,
        string message,
        string confirmText = "Confirm",
        bool danger = false,
        IReadOnlyList<string>? details = null)
    {
        // a new question replaces an unanswered one — the old caller gets "no"
        // instead of hanging forever
        pending?.TrySetResult(false);

        pending = new TaskCompletionSource<bool>();
        Current = new ConfirmRequest(title, message, confirmText, danger, details ?? []);
        Changed?.Invoke();

        return pending.Task;
    }

    public void Answer(bool confirmed)
    {
        var answer = pending;
        pending = null;
        Current = null;
        Changed?.Invoke();

        answer?.TrySetResult(confirmed);
    }
}

The host component

Rendered once, in the main layout. It subscribes to Changed, shows the modal whenever Current is set, and reports the button press back through Answer. Closing the overlay (click outside, Escape) counts as "no".

Components/ConfirmHost.razor 
@implements IDisposable
@inject ConfirmService Confirm

@if (Confirm.Current is { } request)
{
    <ModalOverlay OnClose="() => Confirm.Answer(false)" CssClass="confirm">
        <h3>@request.Title</h3>
        <p>@request.Message</p>

        @if (request.Details.Count > 0)
        {
            <ul>
                @foreach (var detail in request.Details)
                {
                    <li>@detail</li>
                }
            </ul>
        }

        <div class="form-actions">
            <button type="button" class="btn-cancel" @onclick="() => Confirm.Answer(false)">Cancel</button>
            <button type="button" class="@(request.Danger ? "btn-delete" : "btn-save")"
                    @onclick="() => Confirm.Answer(true)">@request.ConfirmText</button>
        </div>
    </ModalOverlay>
}

@code {
    protected override void OnInitialized() => Confirm.Changed += OnChanged;

    // the event can fire from any thread's continuation — marshal back to the renderer
    private void OnChanged() => InvokeAsync(StateHasChanged);

    public void Dispose() => Confirm.Changed -= OnChanged;
}

Registration

Scoped, so each browser tab (Blazor Server circuit or WASM instance) has its own — one user's confirmation can never appear on another user's screen. Drop the host into the layout once:

Program.cs + Layout/MainLayout.razor 
builder.Services.AddScoped<ConfirmService>();

// MainLayout.razor, once, anywhere in the markup:
// <ConfirmHost />

Calling it

The optional details list is for "here's exactly what will happen" — the confirm dialog doubles as a summary of what's about to be saved. danger: true switches the button to the destructive style.

Pages/CustomerOrders.razor 
@inject ConfirmService Confirm

@code {
    private async Task CreateAsync()
    {
        var lines = request.Lines.Where(l => l.Amount > 0).ToList();

        if (!await Confirm.AskAsync(
                "Create customer order",
                $"Create an order for customer {request.CustomerId}?",
                "Create",
                details: lines.Select(l => $"{l.Amount} × {l.Barcode}").ToList()))
            return;   // user said no (or closed the dialog)

        busy = true;
        var result = await CustomerOrderService.CreateAsync(request);
        busy = false;
        // ...
    }

    private async Task DeleteAsync(Product product)
    {
        if (!await Confirm.AskAsync("Delete product", $"Delete {product.Name}?", "Delete", danger: true))
            return;

        await ProductService.DeleteAsync(product.Id);
    }
}

Things to watch

  • Always unsubscribe. ConfirmHost implements IDisposable and removes its handler; a scoped service outlives a re-rendered layout, and a leaked handler keeps calling StateHasChanged on a dead component.
  • One dialog at a time. Asking a second question before the first is answered resolves the first as "no" instead of stacking dialogs — which is what you want for double-clicked buttons.
  • Scoped in Blazor Server means per-circuit. That's the right lifetime here; a singleton would share one dialog between every connected user — the same per-user isolation concern the Toast Notification Service page raises about static events.
  • Guard the button too. Keep busy in the disabled expression so the user can't open the dialog twice while the save is running.
