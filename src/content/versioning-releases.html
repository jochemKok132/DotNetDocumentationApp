Versioned Releases & Auto-Deploy

Tag a GitHub Release, and the server updates to it automatically — no manual git pull, no SSH session, no nginx reload. The trick is a single current symlink: deploying is just re-pointing it, so it's also the instant rollback mechanism.

Why a symlink instead of deploying into one fixed folder

Deploying straight into the folder nginx serves from means there's a window — however short — where half the new files are written and half the old ones remain, and a request landing in that window gets a broken mix of versions. Writing each release into its own folder and only then flipping one symlink avoids that window entirely: nginx resolves the symlink fresh on every request, so from nginx's point of view the switch is a single atomic step, not a gradual overwrite.

layout on the server 
/var/www/docs/
├── releases/
│   ├── v1.0.0/        ← full build output, never touched again
│   ├── v1.1.0/
│   └── v1.2.0/
└── current -> releases/v1.2.0/   ← nginx always reads through here

Rolling back a bad release is ln -sfn releases/v1.1.0 current — no rebuild, no redeploy, just pointing the symlink at a folder that's already known to work.

What "version" means here: package.json, read at build time

The version number isn't invented at deploy time — it's whatever's already in package.json, which a GitHub Release bump is what actually changes. build.js reads it once and stamps it into every page's footer, so the running site can always tell you exactly which release it is.

package.json 
{
  "name": "your-docs-site",
  "version": "1.2.0",
  "private": true,
  "scripts": { "build": "node build.js" }
}
build.js (excerpt) 
const VERSION = require('./package.json').version;

// ...per page:
const html = template
  .replace('{{TITLE}}', escapeHtml(item.title))
  .replace('{{SIDEBAR}}', sidebar)
  .replace('{{VERSION}}', escapeHtml(VERSION))
  .replace('{{CONTENT}}', content);

Bumping the version is a deliberate, reviewable change (npm version minor, or editing the field by hand in a PR) — not something CI invents from a commit count or a timestamp. That keeps the number meaningful: "1.2.0" is a decision someone made, not an artifact of how many times the pipeline happened to run.

The workflow: release published → build → ship → swap

Triggering on release: published rather than push to main is the key choice — it means production only ever moves forward when someone deliberately cuts a release (via the GitHub UI or gh release create), never on every merged commit. Day-to-day pushes to main can run their own build-and-test workflow (see CI Pipeline) without ever touching the live site.

.github/workflows/release-deploy.yml 
name: Deploy latest release

on:
  release:
    types: [published]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.release.tag_name }}

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Build static site
        run: node build.js

      - name: Deploy to server (releases/<version> + atomic symlink swap)
        env:
          DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
          DEPLOY_USER: ${{ secrets.DEPLOY_USER }}
          SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          mkdir -p ~/.ssh
          echo "$SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          ssh-keyscan -H "$DEPLOY_HOST" >> ~/.ssh/known_hosts

          TAG="${{ github.event.release.tag_name }}"
          RELEASE_DIR="/var/www/docs/releases/$TAG"

          ssh -i ~/.ssh/deploy_key "$DEPLOY_USER@$DEPLOY_HOST" "mkdir -p '$RELEASE_DIR'"

          rsync -az --delete -e "ssh -i ~/.ssh/deploy_key" \
            ./dist/ "$DEPLOY_USER@$DEPLOY_HOST:$RELEASE_DIR/"

          ssh -i ~/.ssh/deploy_key "$DEPLOY_USER@$DEPLOY_HOST" \
            "ln -sfn '$RELEASE_DIR' /var/www/docs/current"

          # keep the last 5 releases for instant rollback, prune the rest
          ssh -i ~/.ssh/deploy_key "$DEPLOY_USER@$DEPLOY_HOST" \
            "cd /var/www/docs/releases && ls -1dt */ | tail -n +6 | xargs -r rm -rf"

rsync --delete targets the new release's own folder ($RELEASE_DIR), never current — it's only cleaning up stray files within that one fresh directory, not touching whatever's currently live. The symlink swap is the only step that ever changes what nginx is serving.

Three secrets carry the server access: DEPLOY_HOST, DEPLOY_USER, and a private key as DEPLOY_SSH_KEY (the matching public key goes in that user's ~/.ssh/authorized_keys on the server — generate a deploy-only keypair, don't reuse a personal one). Same repository-secrets rule as everywhere else in this project: see CI Pipeline.

Serving through the symlink: the one-line nginx change

nginx needs no reload when a release ships — it was already pointed at current, and the kernel resolves that symlink on every single request. Compare this to the earlier, simpler setup in Dockerizing for nginx, where a bind mount pointed straight at a fixed dist/ folder:

nginx.conf (excerpt) 
location /docs/ {
    alias /var/www/docs/current/;
    try_files $uri $uri.html $uri/ =404;
}

When this pattern is worth it over the simpler bind-mount setup

  • You want releases to be an explicit, reviewable event (cut from the GitHub UI, with release notes) rather than "whatever's on main right now."
  • You want rollback to be instant and not require a rebuild — just re-point the symlink.
  • The deploy target is a single always-on server reachable over SSH. For containerized or multi-instance deployments, the equivalent idea is tagging and pushing a versioned image and rolling it out through your orchestrator instead of symlink-swapping files on disk.
