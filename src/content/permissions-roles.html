Permissions & Role Hierarchy

Every role list used in [Authorize(Roles = ...)] lives once, as a named constant in the Shared project. Controllers, Blazor pages and the nav all reference the same constant, so "who can approve a refund" is answered in exactly one place — and a second small class decides who may hand out which role.

Named permission constants

Authorize(Roles = "...") takes a comma-separated string, so a permission is simply a constant holding that string. Naming it by what it allows (not who it's for) means a role change is a one-line edit instead of a search through every controller.

Shared/Common/Permissions.cs 
public static class Permissions
{
    public const string Employees      = "Admin,Manager,Support,ShiftLeader,Cashier,FloorWorker,Tester";
    public const string ManageStock    = "Manager,Admin";
    public const string ViewOrders     = "Admin,Manager,ShiftLeader,Cashier,FloorWorker,Tester";
    public const string ManageOrders   = "ShiftLeader,Manager,Admin";

    // a permission can be built from another one when they should always match
    public const string ReceiveOrders  = WriteOffStock;
    public const string WriteOffStock  = "Admin,Manager,ShiftLeader,Cashier,FloorWorker";

    // the same check, usable on a ClaimsPrincipal in code
    public static bool Allows(this ClaimsPrincipal user, string roles) =>
        roles.Split(',').Any(user.IsInRole);

    // "can open the screen": either allowed to manage, or the view-only role
    // that sees everything but can't change it (see View-Only Role Guard)
    public static bool CanOpen(this ClaimsPrincipal user, string manageRoles) =>
        user.Allows(manageRoles) || user.IsInRole(AccessRules.ViewOnlyRole);
}

Using it on the API side

Attributes only accept compile-time constants — which is exactly what const string is — so nothing about the controller changes except that the roles are no longer typed out:

API/Controllers/OrderController.cs 
[Authorize(Roles = Permissions.ViewOrders)]
[HttpGet]
public async Task<IActionResult> GetAllAsync() { ... }

[Authorize(Roles = Permissions.ManageOrders)]
[HttpPost]
public async Task<IActionResult> CreateAsync(CreateOrderRequest request) { ... }

Using it on the frontend

The same constants drive what the UI offers, so the buttons a user sees and the endpoints the API accepts can't drift apart:

Pages/Orders.razor 
@code {
    private bool canManage;
    private bool canReceive;

    protected override async Task OnInitializedAsync()
    {
        var authState = await AuthStateProvider.GetAuthenticationStateAsync();

        // CanOpen: managers can use it, the view-only role can see it (disabled)
        canManage  = authState.User.CanOpen(Permissions.ManageOrders);
        canReceive = authState.User.CanOpen(Permissions.ReceiveOrders);
    }
}

A role hierarchy for "who can assign what"

Permissions answer "what may this role do". A separate question — "which roles may this user create or edit" — needs an ordering. One array defines it; position is rank, and everything else is derived from that:

Shared/Common/RoleHierarchy.cs 
public static class RoleHierarchy
{
    public const string OnlyLowerRoles = "You can only give out roles below your own.";

    // highest first — index is the rank
    private static readonly EmployeeRoleDto[] Order =
    [
        EmployeeRoleDto.Admin,
        EmployeeRoleDto.Tester,
        EmployeeRoleDto.Manager,
        EmployeeRoleDto.Support,
        EmployeeRoleDto.ShiftLeader,
        EmployeeRoleDto.Cashier,
        EmployeeRoleDto.FloorWorker,
    ];

    // only these roles may manage other employees at all
    private static readonly EmployeeRoleDto[] Managers = [EmployeeRoleDto.Admin, EmployeeRoleDto.Manager];

    public static int Rank(EmployeeRoleDto role)
    {
        int index = Array.IndexOf(Order, role);
        return index < 0 ? int.MaxValue : index;   // unknown role = lowest possible
    }

    public static bool IsBelow(EmployeeRoleDto actor, EmployeeRoleDto target) =>
        Rank(actor) < Rank(target) && target != EmployeeRoleDto.None;

    // can manage employees at all AND the target is strictly lower than the actor
    public static bool CanManage(EmployeeRoleDto actor, EmployeeRoleDto target) =>
        Managers.Contains(actor) && IsBelow(actor, target);

    // feeds the role dropdown in the "add employee" form
    public static IEnumerable<EmployeeRoleDto> AssignableRoles(EmployeeRoleDto actor) =>
        Order.Where(role => CanManage(actor, role));

    // roles that shouldn't even show up in lists for non-admins
    public static IReadOnlyList<EmployeeRoleDto> HiddenFrom(EmployeeRoleDto viewer) =>
        viewer == EmployeeRoleDto.Admin ? [] : [EmployeeRoleDto.Admin, EmployeeRoleDto.Tester];

    // the role a signed-in user actually holds
    public static EmployeeRoleDto EmployeeRole(this ClaimsPrincipal user) =>
        Order.FirstOrDefault(role => user.IsInRole(role.ToString()), EmployeeRoleDto.None);
}

The service layer enforces it too — the dropdown is a convenience, not security. Creating or editing an employee checks CanManage(actor, newRole) and, when editing, CanManage(actor, existingRole), and throws if either fails, so a hand-crafted request can't promote someone above the caller.

Things to watch

  • Constants only. Roles = Permissions.X must be a const; a static readonly field won't compile in an attribute. That's the reason these are strings, not arrays.
  • Role names are claim values. They must match what JWT Authentication puts in the role claim — role.ToString() on the enum keeps the two in step.
  • Unknown means lowest. Rank returns int.MaxValue for anything not in the array, so a role someone forgets to add can never outrank a real one.
  • Pair with the guard. View-Only Role Guard covers the role that is listed on every read permission above but on no write one.
