View-Only Role Guard

A demo, tester or auditor account that can open every screen but can't change anything — enforced once, in a single middleware, by HTTP method. No per-controller attribute to forget, and no risk of a new endpoint accidentally being writable.

Why a middleware instead of an attribute

The obvious approach is to leave write endpoints off the view-only role's [Authorize(Roles = ...)] list. That works until someone adds a new endpoint and lists the role "because it needs to see the page" — and a POST that the role should never reach is suddenly open. A guard that looks at the request method instead of the endpoint can't be bypassed by a new controller: if the caller is view-only and the method isn't GET/HEAD/OPTIONS, the request stops here.

The shared rules

The role name, the refusal message and the "is this method read-only" check live in the Shared project, so the API and every frontend agree on them without duplicating strings.

Shared/Common/AccessRules.cs 
public static class AccessRules
{
    public const string ViewOnlyRole = nameof(EmployeeRoleDto.Tester);
    public const string ViewOnlyMessage = "This is a view-only account. Nothing was saved.";

    public static bool IsReadOnlyMethod(string method) =>
        method.Equals("GET", StringComparison.OrdinalIgnoreCase) ||
        method.Equals("HEAD", StringComparison.OrdinalIgnoreCase) ||
        method.Equals("OPTIONS", StringComparison.OrdinalIgnoreCase);
}

The middleware

It answers with the same ApiResponse envelope as every other failure, so the frontend's normal error handling shows the message without a special case.

API/ViewOnlyGuard.cs 
public class ViewOnlyGuard(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context)
    {
        if (context.User.IsInRole(AccessRules.ViewOnlyRole) &&
            !AccessRules.IsReadOnlyMethod(context.Request.Method) &&
            !IsLogin(context.Request.Path))
        {
            context.Response.StatusCode = StatusCodes.Status403Forbidden;
            await context.Response.WriteAsJsonAsync(ApiResponse<object>.Fail(AccessRules.ViewOnlyMessage));
            return;
        }

        await next(context);
    }

    // logging in is a POST, and a view-only user still has to be able to do it
    private static bool IsLogin(PathString path) =>
        path.Value?.EndsWith("/Login", StringComparison.OrdinalIgnoreCase) ?? false;
}

Pipeline position matters

context.User is only populated after authentication has run, and the guard should reject before authorization spends any time evaluating policies, so it sits between the two:

API/Program.cs 
app.UseAuthentication();
app.UseMiddleware<ViewOnlyGuard>();   // after authentication (needs the user), before authorization
app.UseAuthorization();

Mirror it in the UI so the buttons aren't a surprise

The server is the real enforcement, but a view-only user shouldn't be able to fill in a form and only then be told no. Frontends read the same constants and disable the action up front, with the shared message as the tooltip:

Pages/Orders.razor 
<button class="btn-save"
        disabled="@(busy || viewOnly)"
        title="@(viewOnly ? AccessRules.ViewOnlyMessage : null)"
        @onclick="CreateAsync">Create order</button>

@code {
    private bool viewOnly;

    protected override async Task OnInitializedAsync()
    {
        var authState = await AuthStateProvider.GetAuthenticationStateAsync();
        viewOnly = authState.User.IsInRole(AccessRules.ViewOnlyRole);
    }
}

Testing it without a server

A middleware is just a class taking a RequestDelegate, so it needs no test host: pass a delegate that records whether it was reached, build a DefaultHttpContext with the claims and method you want, and assert on the status code and the flag.

UnitTests/Api/ViewOnlyGuardTests.cs 
public class ViewOnlyGuardTests
{
    private static (ViewOnlyGuard guard, Func<bool> nextCalled) CreateSut()
    {
        bool called = false;
        var guard = new ViewOnlyGuard(_ => { called = true; return Task.CompletedTask; });
        return (guard, () => called);
    }

    private static DefaultHttpContext Request(string method, string path, string? role)
    {
        var claims = role is null ? Array.Empty<Claim>() : [new Claim(ClaimTypes.Role, role)];
        var context = new DefaultHttpContext { User = new ClaimsPrincipal(new ClaimsIdentity(claims, "test")) };
        context.Request.Method = method;
        context.Request.Path = path;
        context.Response.Body = new MemoryStream();
        return context;
    }

    [Theory]
    [InlineData("POST", "/Product/Create")]
    [InlineData("PUT", "/Product/Update")]
    [InlineData("DELETE", "/Product/SoftDelete/1")]
    public async Task InvokeAsync_ViewOnlyChanges_Returns403AndSkipsEndpoint(string method, string path)
    {
        var (sut, nextCalled) = CreateSut();
        var context = Request(method, path, AccessRules.ViewOnlyRole);

        await sut.InvokeAsync(context);

        Assert.Equal(StatusCodes.Status403Forbidden, context.Response.StatusCode);
        Assert.False(nextCalled());
    }

    [Fact]
    public async Task InvokeAsync_ViewOnlyLogsIn_CallsEndpoint()
    {
        var (sut, nextCalled) = CreateSut();
        var context = Request("POST", "/Employee/Login", AccessRules.ViewOnlyRole);

        await sut.InvokeAsync(context);

        Assert.True(nextCalled());
    }

    [Fact]
    public async Task InvokeAsync_ManagerChanges_CallsEndpoint()
    {
        var (sut, nextCalled) = CreateSut();
        var context = Request("POST", "/Product/Create", "Manager");

        await sut.InvokeAsync(context);

        Assert.True(nextCalled());
    }
}

Things to watch

  • It's a blunt instrument on purpose. Any non-GET is refused, including harmless ones like a search that was built as a POST with a filter body. Keep reads on GET (see Generic Pagination Pattern) or add an explicit allow-list like the login path.
  • Pair it with the role list. The view-only role still needs to appear in the roles of every read endpoint it should see — see Permissions & Role Hierarchy for how that's kept in one place.
  • Test every branch. Refused writes, allowed reads, the login exception and a normal role passing straight through are four different paths — the tests above cover each. For the broader testing approach see Unit Testing with Moq.
